# Spec: MEME v0

_Draft 1, 2026-10-17. Status: **approved.** The first version of the MEME protocol: identity, records, files and scape bundles ([../protocol/overview.md](../../docs/protocol/overview.md#how-the-protocol-is-built)). Databases, functions, sync and labels come in later versions. It lives in the `scape-protocol` repository with its reference library, test vectors and conformance suite._

**MEME** is a placeholder. The token appears in exactly the places listed under [Where the name appears](#where-the-name-appears), so a rename is one search.

## Principles

- **Borrow, don't invent.** JSON, RFC 8785 canonical JSON, Ed25519, SHA-256, Multikey, DNS, HTTP, SPDX license IDs, JSON Schema.
- **Everything published is self-verifying.** A reader needs only the data and the account's key log, never trust in the host that served it.
- **Version fields everywhere.** Every signed object carries `"v": 0`.
- **Small.** If M0–M2 don't need it, it isn't in v0. But anything that would be expensive to retrofit (completeness, evolution, algorithm agility, scoped keys) is designed in now. What v1 adds is in [meme-v1-notes.md](v1-notes.md).

## Evolution

These rules let the protocol change for decades without breaking old data or old readers:

- **Readers ignore what they don't know.** Unknown fields in any object, and unknown values in any enum-like field, are ignored, not rejected. Signatures still cover them, because a signature covers all the bytes.
- **The one exception: restrictions fail closed.** A reader that meets an unknown field inside a key's restrictions (see [The key log](#the-key-log)) treats the key as unusable. Ignoring a limit would grant more than the signer intended.
- **Envelopes change only with `v`.** No new top-level field appears in a key log entry, record, log entry or checkpoint without a new `v`.
- **Types grow additively.** A type's schema may gain optional fields and new enum values. It may never remove, rename or retype a field, or tighten a limit. A breaking change is a new type.
- **Schemas are open.** Type schemas allow additional properties, so a record written by a newer client still validates on an older host. The 64 KiB body limit bounds what extra fields can carry.

## Encodings

| Thing | Encoding |
|---|---|
| Canonical bytes of a JSON object | **JCS** ([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)), UTF-8 |
| Numbers inside signed objects | **Integers only**, within ±(2⁵³−1). Anything fractional is a string. This avoids canonicalization pitfalls |
| Hashes | SHA-256. **Hash references carry their algorithm:** `sha256:<lowercase hex>` for CIDs and every `prev`/`head` link. File refs name it by key (`{ "sha256": … }`), and file URLs use bare hex so they stay Blossom- and Nostr-compatible. A future algorithm is a new prefix or key, never a reinterpretation |
| Public keys | Ed25519 as **Multikey** (`z6Mk…`, base58btc), as in `did:key` |
| Signatures | Ed25519 ([RFC 8032](https://www.rfc-editor.org/rfc/rfc8032)), base64url without padding. Verification is strict RFC 8032 (canonical encodings, no ZIP-215 leniency), so every implementation accepts exactly the same signatures |
| Account IDs | 24 characters of lowercase base32 (`[a-z2-7]`), 120 bits |
| Times | RFC 3339 UTC with milliseconds: `2026-10-17T09:00:00.000Z` |
| Licenses | An SPDX identifier (`CC-BY-4.0`), `LicenseRef-scape-1.0`, `LicenseRef-all-rights-reserved`, or an `https:` URL to custom terms |

**Signing an object** means: remove its `sig` field, take the JCS bytes, sign them. The signature's algorithm is the signing key's (Multikey names it), so keys are algorithm-agile too. Its **CID** (content ID) is `sha256:` plus the SHA-256 of those same unsigned bytes. The CID doesn't depend on the signature, so it is stable and can't be altered by re-signing.

## Identity

### The key log

Every account, personal or shared, has a **key log**: an append-only chain of signed entries. Each entry states the account's **whole current state**, so a reader never has to replay operations.

```json
{
  "v": 0,
  "account": "k3q7m2xw5yzr4tbd6nc2hjfa",
  "seq": 1,
  "prev": "sha256:9f2c…e1",
  "rotationKeys": ["z6MkhaXg…"],
  "signingKeys": {
    "main":  { "key": "z6Mkf5rG…" },
    "phone": { "key": "z6MkpT8w…", "restrict": { "types": ["post", "file"] } }
  },
  "revokedKeys": [],
  "handles": ["ada.scape.com.de"],
  "hosts": ["https://scape.com.de"],
  "created": "2026-10-17T09:00:00.000Z",
  "sig": { "key": "z6MkhaXg…", "value": "…" }
}
```

| Field | Rule |
|---|---|
| `account` | `null` in the genesis entry; the account ID in every later one |
| `seq`, `prev` | `seq` starts at 0 and rises by 1. `prev` is `sha256:` plus the SHA-256 of the previous entry's full JCS bytes, `sig` included; `null` at genesis |
| `rotationKeys` | 1–5 keys, in priority order, allowed to sign the **next** entry |
| `signingKeys` | 1–8 named keys that sign records, checkpoints and sign-in proofs. Names are `[a-z0-9-]{1,32}`. Each is `{ "key", "restrict"? }` |
| `signingKeys.*.restrict` | Optional limits, so an app or device can sign for itself without holding the account's full authority. v0 defines one: `types`, the record types the key may sign. A restricted key can never sign checkpoints or sign-in proofs. More limits (expiry, rate) come later, and an unknown one makes the key unusable ([Evolution](#evolution)). Scape's host issues only unrestricted keys in v0, but every reader enforces `restrict` from day one |
| `revokedKeys` | Keys whose signatures are no longer trusted, **past ones included**: for a stolen key. A key that is simply removed (rotated out) keeps its past signatures valid |
| `handles` | 0–4 claimed handles. A claim alone proves nothing (see [Handles](#handles)) |
| `hosts` | 1–4 base URLs of hosts serving this account, preferred first. `https:` only, except `http://localhost` and `http://127.0.0.1` for development |
| `deactivated` | Optional `true`. The account is closed and signs nothing more |
| `sig` | Genesis: by one of its own `rotationKeys`. Later entries: by a `rotationKeys` entry of the **previous** state |

**Account ID** (opaque; never parse it) = the first 24 characters of the base32 encoding of SHA-256(JCS(genesis entry, `sig` included)). The ID is derived from the genesis entry, which contains the first keys, so it is self-certifying while keys rotate freely. (This is how `did:plc` works. It refines identity.md's "derived from its first public key".)

**Forks.** In v0, an account's host accepts only the next `seq` after the head it already holds, so it never stores two entries with the same `seq`. A reader that sees two valid entries with the same `seq` treats the account as **disputed** and trusts neither branch. Recovery rules (a higher-priority rotation key overriding a recent entry within a time window) arrive in v1 with self-custody (M6).

**Custody in v0.** Scape's host generates both the rotation key and the signing key, wraps them with Cloud KMS, and signs on the account's behalf. Self-custody adds the user's own rotation key ahead of the host's (M6).

### Handles

- A handle is a **DNS name**: `ada.scape.com.de`, or a domain the account owns (M5). The app shows `ada` for Scape handles.
- **Scape handles:** one DNS label, `[a-z0-9]([a-z0-9-]{1,28}[a-z0-9])?` (3–30 characters), not on the reserved list.
- **A handle is valid only when both directions agree:**
  1. The latest key log entry lists it in `handles`, **and**
  2. The handle points back at the ID, by either a DNS TXT record at `_meme.<handle>` with value `id=<account id>`, or `https://<handle>/.well-known/meme-id` returning the ID as `text/plain`.
- For `*.scape.com.de`, Scape's edge answers the HTTPS method.
- **Reserved:** every first-party scape name (`music`, `map`, `search`, `www`, `api`, `app`, `admin`, `help`, `status`, `mail`, …), brand and impersonation-prone names, and anything offensive. The list lives in the protocol repo's host guidance, not in this spec, because it is host policy.

### Finding an account's host

Given an ID, a reader needs a key log to learn its `hosts`. In v0:

1. References between accounts may carry a **host hint**.
2. Any host may serve the key log of any account it knows. Because entries are self-verifying, a mirror can't forge one, only withhold.
3. Scape's host serves key logs for every account it has seen, acting as a directory.

This is the weakest part of v0, and it is honest about it: a host can withhold the newest entry. v1 adds the sync stream and key transparency ([meme-v1-notes.md](v1-notes.md#key-transparency)).

### Sign-in proofs

Any app or host can learn that a visitor controls an account **without trusting the host that serves it**. The visitor presents a signed proof, and the app checks it against the key log.

```json
{
  "v": 0,
  "account": "k3q7m2xw5yzr4tbd6nc2hjfa",
  "audience": "https://example.app",
  "nonce": "b64url, at least 16 random bytes, issued by the audience",
  "issued": "2026-10-17T09:00:00.000Z",
  "expires": "2026-10-17T09:05:00.000Z",
  "keylogSeq": 3,
  "sig": { "key": "main", "value": "…" }
}
```

**An app accepts a proof when:** `audience` is exactly its own origin; it issued `nonce` and hasn't seen it used; now falls between `issued` and `expires`, which are at most 5 minutes apart; the key at `keylogSeq` is unrestricted and not revoked; and the signature verifies.

- **How the proof is produced** is outside the protocol: a self-custody key in a browser extension or wallet, a remote signer, or, for custodial accounts, the host after the user signs in to it (with a passkey, say).
- **Relation to OpenID Connect.** Sign in with Scape (M5) is OIDC on top of this: its `sub` is the account ID, so an app that later switches to verifying proofs directly sees the same identity. Neither is tied to Scape's host.
- **Not built in M0.** The format is fixed now so that Nostr sign-in (M3), OIDC (M5) and self-custody (M6) all land on the same identity.

## Records

A record is a typed, signed JSON object in an account's repository, addressed by **account + type + key**. Changing a record publishes a new **revision** that points to the previous one.

```json
{
  "v": 0,
  "account": "k3q7m2xw5yzr4tbd6nc2hjfa",
  "type": "profile",
  "rkey": "self",
  "prev": null,
  "created": "2026-10-17T09:00:00.000Z",
  "license": "LicenseRef-scape-1.0",
  "body": { "displayName": "Ada" },
  "keylogSeq": 0,
  "sig": { "key": "main", "value": "…" }
}
```

| Field | Rule |
|---|---|
| `type` | **Core types** are one segment, `[a-z][a-z0-9]*`, and are defined in the protocol's type registry. **Extension types** are reverse-DNS with at least three segments (`com.example.recipe`) and are defined by whoever owns that domain |
| `rkey` | `[a-z0-9][a-z0-9-]{0,63}`. Hosts generate time-sortable keys by default; singletons use `self` |
| `prev` | CID of the previous revision, or `null` for the first |
| `license` | Optional. Absent means the host's default; Scape's default is `LicenseRef-scape-1.0` |
| `body` | Valid against the type's schema. At most 64 KiB of JCS bytes |
| `deleted` | Optional `true` with `body: null`: a **tombstone**, the signed deletion request. Well-behaved hosts drop earlier revisions when they see it |
| `keylogSeq` | The key log entry whose `signingKeys` contained the signing key at signing time |
| `sig.key` | A name in that entry's `signingKeys` |

**A record is valid when:** its schema checks pass; the key log entry at `keylogSeq` exists and lists `sig.key`; that key's `restrict` (if any) permits this `type`; the signature verifies; and that key does not appear in `revokedKeys` of the account's latest entry.

**Visibility is not in the record.** It is the host's access control. Private records never leave the host; v0's read interface serves only public records. Changing visibility doesn't change the record; it adds an entry to the [repository log](#the-repository-log).

### References

Bodies point at other things with plain objects, never URIs, so no protocol name is baked into signed data:

| Ref | Shape |
|---|---|
| **File** | `{ "sha256": "…", "size": 1234, "mime": "image/jpeg" }` |
| **Record** | `{ "account": "…", "type": "…", "rkey": "…", "cid": "…"? , "host": "https://…"? }`. With `cid`, a pinned revision; without, the latest |
| **Account** | `{ "account": "…", "host": "https://…"? }` |

### Core types in v0

| Type | `rkey` | Body |
|---|---|---|
| `profile` | `self` | `displayName` (≤ 64 chars), `bio` (≤ 1000), `avatar` (file ref, image only) |
| `file` | generated | A published file: `blob` (file ref), `name` (≤ 255), `alt` (≤ 2000), optional `width`, `height`, `durationMs` |
| `scape` | the scape's slug | A scape bundle manifest (see [Scape bundles](#scape-bundles)) |

Each type is a JSON Schema in `protocol/types/<type>.json`. Adding a type follows the `scape-record-type` skill.

## The repository log

Revision chains say how one record changed. The **repository log** says what an account has made public, in order, so a reader can tell it has **everything**, and can sync by asking for "all changes after #N". It is also the natural unit for splitting sync across machines: one account, one ordered log.

The sequence lives in the log, not inside records. Making a private record public, or withdrawing a public one, then needs no new revision, and private records leave no gaps a reader could mistake for withheld data.

### Log entries

```json
{ "v": 0, "seq": 42, "prev": "sha256:…", "op": "put", "type": "profile", "rkey": "self", "cid": "sha256:…" }
```

| Field | Rule |
|---|---|
| `seq` | Starts at 1 and rises by 1, per account |
| `prev` | `sha256:` plus the SHA-256 of the previous entry's JCS bytes; `null` for `seq` 1 |
| `op` | `put`: the revision `cid` is now public (a tombstone is a `put` too). `withdraw`: `type`/`rkey` is no longer public; hosts drop their copies as they would for a deletion |
| `cid` | With `put` only |

Log entries are unsigned. They are bound together by `prev` and vouched for by checkpoints.

### Checkpoints

```json
{ "v": 0, "account": "k3q7…", "seq": 42, "head": "sha256:…", "created": "2026-10-17T09:00:00.000Z", "keylogSeq": 0, "sig": { "key": "main", "value": "…" } }
```

- `head` is the hash of log entry `seq`. Signed by an unrestricted signing key.
- A host publishes a new checkpoint whenever the log has grown, at least once a minute while it is changing.
- **Verifying completeness:** take a checkpoint you trust at `seq` *a*, fetch entries *a*+1 … *b*, recompute the chain, and check it ends at the `head` of a checkpoint for *b*. A missing, reordered or altered entry breaks the chain.
- Inclusion proofs for single entries (a Merkle structure over the log) come in v1 ([meme-v1-notes.md](v1-notes.md#inclusion-proofs)). The hash chain already makes the format compatible.

## Files

A file is a blob named by its SHA-256. Anyone can check that the bytes match the name.

- **Fetch:** `GET {files}/{sha256}` returns the bytes; `HEAD` returns their size and type. `{files}` comes from the host descriptor. With `{files}` at a domain's root this is **Blossom (BUD-01)-compatible**, ready for the Nostr bridge.
- **Serving rules:** files are served from an origin that runs no app code (the user-content domain, open question 2 in [../decisions.md](../../docs/decisions.md#open-questions)), with `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox; default-src 'none'`.
- **Public only in v0.** Private files reach their owners through the host's own signed, expiring URLs, outside the protocol.
- **Upload is not in v0.** Uploading belongs to the host's functions and the safety pipeline (M1). Nothing reaches `{files}` until the pipeline clears it.

## Scape bundles

A scape is published as a revision of a `scape` record. Its body is the **manifest**; every file it lists is a content-addressed blob. One signature covers the whole site.

```json
{
  "title": "Ada's links",
  "entry": "index.html",
  "files": {
    "index.html":        { "sha256": "…", "size": 2210, "mime": "text/html" },
    "assets/site.css":   { "sha256": "…", "size": 940,  "mime": "text/css" },
    "404.html":          { "sha256": "…", "size": 512,  "mime": "text/html" }
  },
  "blocks": [ { "name": "scape/link-list", "version": "1.0.0", "manifest": { "sha256": "…", "size": 410, "mime": "application/json" } } ],
  "uses": { "records": [ … ], "functions": [ "account.get" ] },
  "generator": "scape-compiler/0.1.0"
}
```

| Field | Rule |
|---|---|
| `entry` | A key of `files`; served at `/` |
| `files` | Path → file ref. Paths are relative, `/`-separated, case-sensitive, at most 256 characters, from `[A-Za-z0-9._~-/]`, with no empty, `.` or `..` segment. At most 10,000 files and 1 GiB in total |
| `blocks` | The block versions the scape was built from, pinned by their manifest's hash ([block-format.md](../../docs/specs/block-format.md)) |
| `uses` | What the scape reads and calls, so readers, moderators and hosts can see it without running it |
| `generator` | Optional. What produced the bundle |

**Serving a bundle at any address:** `/` → `entry`; `/p` → `p` if present, else `p/index.html`; `/p/` → `p/index.html`; anything else → `404.html` with status 404 if present. Any static host can do this, so any host can serve any scape.

**Exporting** a scape writes its files at their paths plus `scape.json`, the signed record. Importing the folder anywhere reproduces and verifies it.

## The host interface (read-only)

| Request | Returns |
|---|---|
| `GET /.well-known/meme` | The host descriptor: `{ "v": 0, "api": "https://scape.com.de/meme/v0", "files": "https://…/" }` |
| `GET {api}/accounts/{id}/keylog` | `{ "entries": [ … ] }`, genesis first |
| `GET {api}/accounts/{id}/checkpoint` | The latest checkpoint |
| `GET {api}/accounts/{id}/log?after=&limit=` | Repository log entries with `seq` greater than `after`, oldest first, at most 1,000 per page |
| `GET {api}/accounts/{id}/records/{type}?limit=&cursor=` | Latest revisions of public records of a type, newest first, `{ "records": [ … ], "cursor": … }` |
| `GET {api}/accounts/{id}/records/{type}/{rkey}` | The latest revision, or the tombstone |
| `GET {api}/accounts/{id}/records/{type}/{rkey}/revisions` | Every revision the host still holds, newest first |
| `GET {api}/handles/{handle}` | `{ "account": "…" }`. A convenience; the DNS and HTTPS checks above are authoritative |
| `GET {files}/{sha256}` | The blob |

Errors are `{ "error": { "code", "message" } }` with the codes and statuses of [the function registry](../../docs/specs/function-registry.md#errors). Responses are `application/json`, CORS-open (`Access-Control-Allow-Origin: *`) and carry no cookies.

## Conformance

The suite lives in the `scape-protocol` repository and has two parts:

1. **Vectors.** JSON fixtures under `vectors/{keylog,record,log,checkpoint,proof,file,scape}/{valid,invalid}/`, each with the expected result and, for invalid ones, the reason. Keys come from fixed seeds, so every signature is reproducible. Any implementation, in any language, can run them.
   Vectors include the evolution rules: records with unknown fields must verify, and keys with unknown restrictions must be refused.
2. **Host checks.** `pnpm conformance --host <url>` reads a fixture account from a live host and checks every endpoint above, the serving rules, the error shapes, and that the repository log and checkpoint agree with the records served.

`make check` runs both against the reference library and a local host. The testing phase ends when a second, independent host passes part 2 ([../engineering/v1-plan.md](../../docs/engineering/v1-plan.md#m6-open-network)).

## Where the name appears

Only here, in wire formats: the `/.well-known/meme` path, the `/meme/v0` API prefix, the `_meme.<handle>` DNS label, and `/.well-known/meme-id`. **None appears inside signed data,** so renaming the protocol before or after launch never invalidates a signature. Rename before wave 1 to avoid a migration of handles' DNS records.

## Not in v0

The sync stream and backfill, key transparency, cross-host private data, chunked file hashes and labels are designed in [meme-v1-notes.md](v1-notes.md). Also not in v0: databases, functions as a protocol layer, upload, key export and recovery windows (M6), custom-domain handles (M5), and Nostr mappings (M3, as a bridge).

## Decisions to approve

1. **JCS + Ed25519 + SHA-256 + Multikey** as the signing stack, **integers only** in signed JSON, and **algorithm-prefixed hashes** (`sha256:…`).
2. **State-based key log** and **account ID = hash of the genesis entry** (a refinement of identity.md), with **scoped signing keys** (`restrict.types`) enforced by readers from day one.
3. **Evolution rules:** readers ignore unknown fields and values, restrictions fail closed, types grow only additively.
4. **A repository log with signed checkpoints**, so readers can prove they have everything and sync incrementally.
5. **Sign-in proofs** as the protocol's own way to prove control of an account; OIDC's `sub` is the account ID.
6. **Handles are DNS names** checked in both directions; Scape handles share the `*.scape.com.de` namespace with first-party scapes, so those names are reserved.
7. **Records:** account + type + rkey, revisions chained by CID, tombstones for deletion, visibility kept outside the record.
8. **Core types are single-segment and unprefixed; extensions are reverse-DNS.** Neither carries the protocol's name.
9. **A scape is a `scape` record** whose body is the manifest, so one signing mechanism covers records and sites.
10. **Files:** Blossom-compatible fetch, served only from the user-content domain, no upload in v0.
